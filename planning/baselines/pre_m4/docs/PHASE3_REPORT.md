# 第三阶段实施与试玩报告

2026年11月6日 · 构建 `phase3-20261106` · M2A/M2B 首轮可玩交付

本轮把八件列表和财富计数替换为唯一物品实例、格子库存、实物仓库、战前配装和可恢复对局。成功撤离带回实物，出售后才增加资产；失败丢失本局携带物品。交付仍为 Windows 原型和 Godot 源码。

## 实现

| 模块 | 内容 |
| --- | --- |
| `scripts/inventory/` | 13 种 Resource 定义；实例、数量、耐久、运行字段；唯一所有权；6×5 / 25 kg 背包、10×12 仓库、装备槽和收件区 |
| 库存事务 | 堆叠、拆分、旋转、手动和自动放置、整理、批量部分拾取；空间、重量、修订号和重复命令验证 |
| 搜索 | 独立随机源生成固定掉落；每 0.7 秒揭示一件；保存顺序、进度和剩余物品；拒绝领取未揭示物品 |
| `scripts/ui/` | 搜索、背包、仓库和装备；数量、价值、重量、耐久；触屏按钮分页和格子预览；界面仅发送意图 |
| `ProfileService` | 配装进入对局容器；成功实物入库，满仓进入收件区；出售和补给购买；失败损失、不可出售的救济装备 |
| `RaidSnapshot` | 保存玩家与九名守卫、位置姿态、生命护甲、枪械、AI 记忆、装填治疗、计时与撤离；随机流状态以字符串保存 |
| `SaveService` | schema/content version、代次、SHA-256 双槽、临时写入/flush/读回验证/重命名、旧档备份、PID 锁和多窗口冲突保护 |

库存命令在副本中验证，持久化成功才发布。合并堆叠可以吸收来源实例 ID，以数量守恒和唯一所有权为准。命令账本有界保留 256 条，容器修订号跨局递增。行动中不能操作营地仓库或更换装备。

结算以 raid_id 记账，在同一次提交中迁移物品、增加撤离次数、清除活动对局。重复结算先查账本；失败重试直接提交终局，不先写阵亡但仍进行中的中间状态。

背包弹药拥有备弹，弹匣属于步枪实例。恢复先应用世界快照，再从物品同步药包、备弹、弹匣和护甲，避免拾取后的旧显示快照吞掉新增弹药。搜索和背包采用暂停规则，关闭后重新输入移动与开火。

## 存档取舍

Windows 源码试玩使用 `res://user_data/saves`，使启动器与开发试玩使用同一目录；正式导出和移动端用 `user://saves`。旧 progress.json 只在没有新档时迁移，保留原件并复制备份，迁移与初始物资标识一起保存。

世界每 10 秒保存；物品、揭示、换弹治疗完成、暂停、返回与正常关窗也保存。强制终止只能恢复最近成功检查点，不承诺逐物理帧重放。导航路径与感知缓存重建，行为状态和最后已知位置恢复。

实际场景写盘发现 Godot 完整精度 JSON 浮点读回存在末位漂移。本次统一规范化保留小数后六位，用同一文本计算与验证校验；整数数量保持精确，64 位随机状态使用字符串。该精度适用于当前米制地图和秒计时。

单槽损坏可恢复另一槽；双槽损坏、更新版本、未知物品或非法快照结构会阻止写入并保留文件。首次建档失败不发布空 profile。临时写入与替换失败不改变已发布库存；旧窗口发现更新代次后拒绝覆盖。首次建档尝试建立两份正式槽。
